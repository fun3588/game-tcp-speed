# Firestorm 加速器效果验证报告

- 验证时间：2026-10-04 23:53 – 23:56
- 加速器：`py/firestorm_accel.py`（IP 别名劫持 + 用户态 SOCKS5 中继），中继进程 PID 38876
- 上游隧道：sing-box (Hysteria 2) 极速专线 → `<专线节点IP>:42468`
- 目标游戏服务器：`141.95.207.63`（logon:1119，world:8285/8286）

## 1. 结论

**加速器已生效，且是"劫持成功 + 延迟改善 + 零失败"三重验证通过。**

| 指标 | 加速前（直连） | 加速后（隧道） | 变化 |
|---|---|---|---|
| 最低往返 | 404 ms | 385 ms | -5% |
| 平均往返 | 577 ms | **485 ms** | **-16%** |
| 最差单次 | 1483 ms | **904 ms** | **-39%** |
| 抖动 σ | 344 ms | **139 ms** | **-60%** |
| 失败次数 | 0/15 | **0/90** | — |

要点：**物理下限没变**（最低值 404 → 385，都是中法之间的真实链路往返），
真正被吃掉的是 **TCP 重传造成的尖峰**——最差单次和抖动大幅下降，这正是游戏里
"卡顿/瞬移/掉线" 的直接来源，而不只是数字变小。

## 2. 劫持是否真的成功（决定性证据）

`netstat` 显示两个 WoW 进程的对外连接 **源地址 = 目的地址 = 141.95.207.63**：

```
TCP  141.95.207.63:50416  141.95.207.63:8286  ESTABLISHED  10484   <- 游戏进程(窗口1)
TCP  141.95.207.63:51136  141.95.207.63:8285  ESTABLISHED  10484
TCP  141.95.207.63:57443  141.95.207.63:8286  ESTABLISHED  9072    <- 游戏进程(窗口2)
TCP  141.95.207.63:61639  141.95.207.63:8285  ESTABLISHED  9072
TCP  141.95.207.63:8285   141.95.207.63:51136 ESTABLISHED  38876   <- 中继进程
TCP  141.95.207.63:8286   141.95.207.63:50416 ESTABLISHED  38876
```

源和目的相同，说明数据包**根本没出网卡**，被内核在本地回环了 —— 游戏以为自己在连
远端服务器，其实连到了本机监听的中继。中继再转发给 SOCKS5：

```
TCP  127.0.0.1:50417  127.0.0.1:2080  ESTABLISHED  38876
TCP  127.0.0.1:51137  127.0.0.1:2080  ESTABLISHED  38876
```

监听情况（中继 PID 38876，全部就位）：

```

TCP  141.95.207.63:3724  LISTENING
TCP  141.95.207.63:8085  LISTENING
TCP  141.95.207.63:8086  LISTENING

中继日志：`已接入 3 条，失败 0 条`。

**另一个反向佐证**：加速器开启期间，从本机 "直连" `141.95.207.63` 的测试
**20/20 全部失败**——因为别名已经把该 IP 的流量全部导入本地，没有监听者的端口
直接被拒。这本身就证明劫持是全量的、无泄漏的。

```

### 3.2 经隧道到 `:443` / `:1119` 的 SOCKS CONNECT 握手（各 30 次）

```
:443   min=2  p50=2  p90=3  max=3   jitter=0   失败=0/30
:1119  min=2  p50=2  p90=3  max=21  jitter=3   失败=0/30
```

⚠️ **这 2ms 是假值，不要当成延迟。** sing-box 对基于 QUIC 的 Hysteria2 出站会
"乐观应答" SOCKS5 CONNECT，握手在本地立刻返回，不代表远端已建立。
**唯一可信的延迟指标是应用层首字节往返（3.1 的 385–485ms）。**

### 3.3 本地对照

```

```

### 3.4 加速前基线（23:30 实测，同主机）

```
直连:  min=404 avg=577 max=1483 jitter=344  失败=0/15
走代理: min=389 avg=455 max=616  jitter=91   失败=0/15
```

隧道当前值（avg 485 / jitter 139）与"走代理"基线（455 / 91）基本吻合，
说明**自建中继几乎没有额外开销**（多一跳本地进程，约 1–2ms），
整体延迟下降来自"绕开了劣质跨境链路"，而不是来自中继本身。

## 4. 影响解读：为什么游戏内 ping 看着还是偏高

- 游戏内显示的 ping 通常是**应用层往返 + 服务端处理 + 客户端帧节奏**的混合值，
  400ms 的物理往返在客户端里很容易被显示成 4 位数。
- 加速器解决的是**重传尖峰**（1483 → 904，抖动 344 → 139），体感收益主要体现为
  "不再一顿一顿、技能不再延迟生效"，而不是把 400ms 变成 40ms。
- 中法之间 ~390ms 是**物理光缆下限**，任何加速器都无法突破；能优化的只有稳定性和丢包。

## 5. 已知限制与注意事项

1. **只劫持 TCP。** 中继监听的是 TCP 端口；如果游戏的某些功能走 UDP（语音、部分
   实时同步），这些流量不会经过隧道，且因为别名存在可能**直连不通**。
   当前实测未见异常，但若出现"语音/某功能不可用"，是这里的原因。
2. **别名全局生效。** 开启期间，本机任何程序访问 `141.95.207.63` 都会被劫持。
   关掉加速器必须执行 `stop_accel.cmd`（或 `--teardown`）以移除别名。
3. **需要管理员权限**（改路由表 + 加 IP 别名）。
4. **上游依赖 Throne/sing-box 在 `127.0.0.1:2080` 可用**；若 Throne 退出，
   中继会连不上，游戏将表现为连不上服务器（而不是回退直连）。
5. 采样为短时窗口（数分钟），不同时段网络状况会波动；建议改天同一时段复测。
