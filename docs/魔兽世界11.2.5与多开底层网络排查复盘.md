## 1. 背景与现象概述

在配合自研原生登录器 `logingui.exe` 批量多开启动《魔兽世界 11.2.5》客户端时，初期遭遇了以下典型故障：
1. **启动或进入世界几秒内客户端崩溃**：报错 `ERROR #8 (0x8) Requested 1398240 bytes ... Images\funcs.cpp(100) Out of Memory`；
2. **连接超时与卡主界面**：登录凭据交换阶段长时间无响应；
3. **多开数量受限**：直连可开多个号，但开启加速器后前两个号正常，第三个号在角色选人界面点击进入世界时必定弹窗报错：
   > **已从服务器断开。(WOW51900319)**

## 2. 死穴一：CDN 贴图流式加载被无差别代理导致内存溢出崩溃 (funcs.cpp Out of Memory)

### 故障日志取证
在游戏崩溃生成的 `Errors/2026-10-17_22.48.54_Error_36652.txt` 中提取关键堆栈：
```text
==============================================================================
Error: ERROR #8 (0x8)
Description: Requested 1398240 bytes of memory
File: d:\BuildServer2\Builder\checkouts\1\Engine\Source\Images\funcs.cpp(100)
<ExceptionType> Out of Memory
----------------------------------------
Streaming diagnostics (Errors):
----------------------------------------
cURL request 'http://146.59.238.42/tpr/wow/config/3c/a5/3ca57fe7319a297346440e4d2a03a0cd' failed with 7 : Couldn't connect to server
Download request 'http://146.59.238.42/tpr/wow/config/3c/a5/3ca57fe7319a297346440e4d2a03a0cd' failed. Code: -1.
Failed to start download. Select failed. Hosts exhausted.
Exhausted all hosts trying to download 3ca57fe7319a297346440e4d2a03a0cd(0, 0).
Failed to download missing config. Error(17) : cdn hosts exhausted
```

### 病因剖析
- 魔兽 11.2.5 客户端内部集成了 libcurl 流式数据加载引擎，启动与进入世界时会并发向 CDN（`146.59.238.42:80`）下载角色模型、贴图配置（BLP）与密钥；
- 旧版 Hook 逻辑将**所有非 127.0.0.1 的 IP**（包括 HTTP 80 和 HTTPS 443）全部拦截并强制接入本地 Socks5 握手；
- 由于在 `connect` 内部强行将套接字临时设为阻塞模式，破坏了 libcurl 基于非阻塞 `select` 状态机的时序，libcurl 报错 `Couldn't connect to server`，导致 CDN 节点资源耗尽；
- 紧接着，游戏贴图解码器 `Engine\Source\Images\funcs.cpp` 试图解压缩空指针或缺失的 BLP 资源，抛出伪装的内存溢出（Out of Memory）错误，游戏瞬间闪退。

## 3. 死穴二：Socks5 握手失败引发二次重连与 WSAEISCONN 脏套接字

### 故障日志取证
在注入日志 `proxy_hook.log` 中捕获到大量如下记录：
```text
[22:47:40.069] [Socks5] 读取 CONNECT 响应头失败
[22:47:40.069] [TCP 错误] Socks5 握手失败: 136.110.153.89:443
```

### 病因剖析
- 魔兽世界后台存在大量暴雪遥测、证书链检查（OCSP: 443 端口）并发短连接；
- 旧版代码在握手失败分支中，没有阻断流程，而是漏到函数末尾再次执行：
  ```cpp
  return pOriginalConnect(s, name, namelen);
  ```
- 此时套接字 `s` 已经在前面成功连上了本地代理 `127.0.0.1:58588`，对一个已经处于 Connected 状态的套接字再次调用 `connect()`，操作系统直接返回 **`WSAEISCONN` (10056: 套接字已连接)**，引发游戏内部网络库致命报错断开。

## 4. 死穴三：ConnectEx 异步 IOCP 连接无握手黑洞

### 病因剖析
- DirectX 12 现代游戏会通过 `WSAIoctl` 动态查询扩展函数指针 `WSAID_CONNECTEX`；
- 旧版代码在拦截 `ConnectEx` 时，直接将目标地址改为了 `127.0.0.1:58588`，但由于其属于基于 `LPOVERLAPPED` 的异步完成端口调用，**完全没有插入 Socks5 握手代答协议**；
- 一旦完成端口被激活，魔兽工作线程向套接字写入原生业务包，Sing-box 由于未收到 Socks5 握手数据直接判定协议违规抛弃，导致该连接沦为黑洞。

## 5. 死穴四：WSAEventSelect 事件二次绑定清空内核事件记录引发多开断开 (WOW51900319)

### 故障现象与事实确认
- 用户实测直连模式下，同一台电脑可以正常开 4 个甚至更多客户端同时在线；
- 开启旧版加速器后，**只能开 2 个，第 3 个在选人界面必定报错 `WOW51900319`**；
- 远程核查海外 VPS 与 Firestorm 官方服务器，证实服务器端**没有任何单 IP 2 开的限制**。

### 深入底层机制：MSDN 的官方规定
在 MSDN 官方文档中，对于 `WSAEventSelect` 有如下铁律：
> **"Issuing a WSAEventSelect for a socket cancels any previous WSAEventSelect or WSAAsyncSelect for the same socket, and clears the internal network event record."**

### 故障时序还原
1. 游戏在调用 `connect()` 之前，已预先绑定了 `WSAEventSelect(s, hEvent, FD_CONNECT | FD_READ | FD_WRITE | FD_CLOSE)`；
2. 旧版 Hook 强行调用 `ioctlsocket(s, FIONBIO, &blk)` 切换阻塞模式并完成本地代理连接与 Socks5 握手；
3. 握手成功后，旧代码执行了恢复逻辑：
   ```cpp
   pOriginalWSAEventSelect(s, ctx.hEvent, ctx.networkEvents); // <-- 致命代码！
   SetEvent(ctx.hEvent);
   ```
4. **这一句二次调用，彻底清空了操作系统内核记录的已就绪网络事件（包括 `FD_WRITE` 可写事件）！**
5. 虽然随后调用了 `SetEvent(ctx.hEvent)` 唤醒游戏线程，但游戏主循环调用 `WSAEnumNetworkEvents` 时，读到的事件标志位全为 0；
6. 在单开或双开时，由于线程调度较快，客户端可能直接尝试写数据侥幸过关；但在多开并发时，魔兽网络库严格遵循事件驱动，**误认为套接字不可写，导致在选人界面一直没有发送 `CMSG_PLAYER_LOGIN`（角色登录包）**；
7. 客户端在此停滞约 30~40 秒后，远端世界服务器因超时主动发送 RST，魔兽客户端随即弹出：
   > **`已从服务器断开。(WOW51900319)`**

## 6. 架构重构方案与代码实现

针对上述全部死穴，我们在 [`c/dll/hook_proxy.cpp`](file:///E:/code/game-tcp-speed/c/dll/hook_proxy.cpp) 中进行了彻底重构：

### 1. 智能流量分流：绝对放行 Web/CDN，精准加速核心游戏业务
```cpp
static bool ShouldAccelerate(const sockaddr_in* target) {
    if (!target) return false;
    unsigned long ip = target->sin_addr.s_addr;
    if (ip == inet_addr("127.0.0.1")) return false; // 环回直连

    int port = ntohs(target->sin_port);

    // 严禁拦截 HTTP 80 与 HTTPS 443！保障 cURL CDN 贴图流式下载与 Web 遥测 100% 顺畅
    // 彻底杜绝 funcs.cpp(100) 贴图解码与 Out of Memory 崩溃
    if (port == 80 || port == 443 || port == 8080) return false;

    // 精准加速魔兽核心通信链路
    // 1119: 战网认证登录 (Logon Portal)
    // 3724: 经典魔兽认证/选服
    // 8285, 8286: Firestorm 世界服务器
    // 8085, 8086: 常见私服世界服务
    if (port == 1119 || port == 3724 || port == 8285 || port == 8286 || port == 8085 || port == 8086) {
        return true;
    }
    if (ip == inet_addr("141.95.207.63")) return true; // Firestorm 官方主服务器
    if (port >= 8000 && port <= 9999) return true;     // 世界服通用高位端口区间

    return false;
}
```

### 2. 无损 select 驱动握手：永不破坏套接字模式与内核事件记录
彻底废除切换阻塞模式与重新调用 `WSAEventSelect` 的做法，使用超时 `select` 精准驱动 Socks5 协议的收发：
```cpp
// 基于 select 驱动的超时发送，天然兼容阻塞与非阻塞套接字
static BOOL SendAllTimed(SOCKET s, const char* buf, int len, int timeoutMs = 2500) {
    int total = 0;
    while (total < len) {
        fd_set wfds;
        FD_ZERO(&wfds);
        FD_SET(s, &wfds);
        timeval tv = { timeoutMs / 1000, (timeoutMs % 1000) * 1000 };
        int sel = select(0, NULL, &wfds, NULL, &tv);
        if (sel <= 0) return FALSE;

        int n = send(s, buf + total, len - total, 0);
        if (n <= 0) {
            if (WSAGetLastError() == WSAEWOULDBLOCK) { Sleep(1); continue; }
            return FALSE;
        }
        total += n;
    }
    return TRUE;
}
```

### 3. 连接与握手全流程无损接管
- 在 `HandleRedirectConnect` 中连接 `127.0.0.1`，遇到非阻塞 `WSAEWOULDBLOCK` 时使用 `select` 等待本地建立连接（耗时 < 1ms）；
- 开启 `TCP_NODELAY = 1` 禁用 Nagle 算法，消除心跳包与操作包 40~200ms 的延迟积压；
- 握手完成后仅唤醒事件句柄，**绝对不调用 `pOriginalWSAEventSelect`**，内核真实的 `FD_CONNECT` 与 `FD_WRITE` 完整保留；
- 对 `ConnectEx` 异步 IOCP 优先放行原生直连，杜绝完成端口黑洞。

## 7. 长生命周期内存治理与 PID 复用防漏注入

### 1. 杜绝 SocketContext 内存泄漏（Hook closesocket）
- 游戏频繁创建与关闭临时短连接，若不处理 `closesocket`，全局 `g_SocketMap` 将无限制膨胀；
- 增加 `HookedClosesocket`：
  ```cpp
  int WSAAPI HookedClosesocket(SOCKET s) {
      {
          std::lock_guard<std::mutex> lock(g_SocketMutex);
          g_SocketMap.erase(s);
      }
      return pOriginalClosesocket(s);
  }
  ```
  套接字关闭时立刻抹除上下文，杜绝内存泄漏与旧属性误继承。

### 2. 自动监控 PID 存活检查（防 PID 复用漏注入）
- 在 `launcher_gui.cpp` 的 `AutoInjectWorker` 中，增加存活进程快照比对；
- 当检测到某个已注入 PID 在系统中已不复存在时，自动将其从 `g_InjectedPids` 移除，确保下次游戏重启并复用同一 PID 时能够毫秒级重新注入接管。

### 3. 日志自动滚动保护
- `WriteLog` 自动监控日志体积，超过 5MB 自动截断重置，杜绝多开长时间挂机导致磁盘日志膨胀。

## 8. 死穴五：进出副本过图时 MinHook 对 ConnectEx 汇编篡改导致 ERROR #132 内存越界崩溃 (v3.1.1)

### 故障日志取证
在 WRobot 自动化挂机刷自由镇（频繁进出副本传送门）场景下，客户端在触发过图时必定闪退：
```text
19:31:33.665  Output.log: World transfer pending...
19:31:34.194  Crash_22864: Exception: ACCESS_VIOLATION - The instruction at "0x00007ff456f7cd42" referenced memory at "0x000001f843ea7ef5". The memory could not be "read".
              Call Stack: DBG-ADDR<00007ff456f7cd42>("<unknown>") <- DBG-ADDR<00007ff7a01c3f3f>("WoW 11.2.5 - Firestorm.exe")
```

### 病因剖析
- 崩溃地址落在 `0x00007ff4...` 匿名可执行内存，属于 MinHook `VirtualAlloc` 分配的 Trampoline（中继跳板）内存页；
- Windows 11 x64 下 `mswsock.dll` 内部指令高度经过编译器优化与控制流防护（CFG）插桩，`ConnectEx` 函数头部包含基于 `RIP` 的相对寻址指令；
- 当 MinHook 将这几条指令搬迁至匿名跳板页执行时，**相对偏移计算失真，指令直接寻址到了未映射的非法野指针地址（`0x000001f843ea7ef5`）**，进入跳板瞬间即抛出 `ACCESS_VIOLATION` 内存读取崩溃；
- 同时，旧版在 `HookedWSAIoctl` 中篡改 `WSAID_CONNECTEX` 扩展指针，形成双重干扰。

### 根治方案 (v3.1.1)
1. **彻底拆除 `mswsock!ConnectEx` 的汇编机器码篡改**：
   - 彻底删除 `TryHookConnectExDirectly()` 以及 `HookedWSAIoctl` 对 `WSAID_CONNECTEX` 的篡改；
   - 绝对不触碰 `mswsock.dll` 任何代码页，让所有底层完成端口 IOCP 扩展完全原生直通，消除跳板内存越界源头。
2. **重构套接字事件绑定的生命周期清理**：
   - 在 `HookedWSAEventSelect` 与 `HookedWSAAsyncSelect` 中，当游戏传入 `NULL / 0` 时，主动从 `g_SocketMap` 中清空句柄映射，杜绝句柄复用导致的悬空信号操作。
